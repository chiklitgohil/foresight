# AI4I 2020 Dataset Profile

## Dataset Summary

The AI4I 2020 predictive maintenance dataset contains 10,000 machine-operation rows with 14 columns. Each row has two identifiers (`UDI`, `Product ID`), one product quality variant (`Type`: L, M, or H), five numeric sensor or operating columns, one binary target label (`Machine failure`), and five binary failure-mode labels (`TWF`, `HDF`, `PWF`, `OSF`, `RNF`). The data is clean and compact, with no missing values, no duplicate rows, and sensor values that appear physically plausible within the dataset ranges.

## Exact Class Balance

- Non-failure rows (`Machine failure = 0`): 9,661 rows, 96.61%.
- Failure rows (`Machine failure = 1`): 339 rows, 3.39%.
- This is a strongly imbalanced binary classification problem. Accuracy alone will be misleading; later evaluation should emphasize recall, precision, F1, PR-AUC, ROC-AUC, and business-cost-aware thresholding.

## Key Findings

- Shape and schema: 10,000 rows and 14 columns. Numeric sensor columns are `Air temperature [K]`, `Process temperature [K]`, `Rotational speed [rpm]`, `Torque [Nm]`, and `Tool wear [min]`.
- Missingness: every column has 0 missing values.
- Target imbalance: only 339 of 10,000 rows are labeled as machine failures.
- Failure mode counts:
  - `TWF`: 46 rows, 0.46%.
  - `HDF`: 115 rows, 1.15%.
  - `PWF`: 95 rows, 0.95%.
  - `OSF`: 98 rows, 0.98%.
  - `RNF`: 19 rows, 0.19%.
- Failure mode overlap:
  - 9,652 rows have no failure mode flags.
  - 324 rows have exactly one failure mode flag.
  - 23 rows have exactly two failure mode flags.
  - 1 row has exactly three failure mode flags.
  - 24 rows have multiple failure mode flags, so failure causes are not always mutually exclusive.
- Pairwise failure mode overlap is highest for `PWF+OSF` with 12 co-flagged rows, followed by `HDF+OSF` with 6 rows. Several pairs have no overlap.
- Numeric summary:
  - Air temperature ranges from 295.3 K to 304.5 K, mean 300.00 K.
  - Process temperature ranges from 305.7 K to 313.8 K, mean 310.01 K.
  - Rotational speed ranges from 1168 rpm to 2886 rpm, mean 1538.78 rpm.
  - Torque ranges from 3.8 Nm to 76.6 Nm, mean 39.99 Nm.
  - Tool wear ranges from 0 min to 253 min, mean 107.95 min.
- Correlation with `Machine failure`:
  - `Torque [Nm]`: 0.191321, the strongest single linear association among numeric inputs.
  - `Tool wear [min]`: 0.105448.
  - `Air temperature [K]`: 0.082556.
  - `Rotational speed [rpm]`: -0.044188.
  - `Process temperature [K]`: 0.035946.
- Numeric feature relationships:
  - Air temperature and process temperature are strongly correlated with each other: 0.876107.
  - Rotational speed and torque are strongly negatively correlated: -0.875027.
- Product quality variant breakdown:
  - `H`: 1,003 rows, 21 failures, 2.09% failure rate.
  - `L`: 6,000 rows, 235 failures, 3.92% failure rate.
  - `M`: 2,997 rows, 83 failures, 2.77% failure rate.
  - The low-quality variant has the highest observed failure rate.
- Data leakage and row ordering:
  - `UDI` is monotonic increasing and unique for every row. It may imply row order, but it is not a timestamp or operational signal.
  - `Product ID` is unique for every row and should not be used as a generalizable predictive feature.
  - Failure mode columns (`TWF`, `HDF`, `PWF`, `OSF`, `RNF`) are diagnostic/outcome labels. They should not be used as input features when predicting overall machine failure in a real deployment.
  - There is no explicit timestamp, equipment history, sequence grouping, maintenance event time, or prediction horizon.
- Data quality:
  - Duplicate full rows: 0.
  - Duplicate rows excluding `UDI` and `Product ID`: 0.
  - Negative air temperature, process temperature, rotational speed, torque, and tool wear readings: 0.
  - Process temperature below air temperature: 0.

## Feature Engineering Ideas

- Mechanical load proxy: combine `Torque [Nm]` and `Rotational speed [rpm]`, for example `torque_x_speed` or an approximate power/load term. Torque has the strongest positive correlation with failure (0.191321), while rotational speed is strongly negatively correlated with torque (-0.875027), so their interaction may capture stress regimes better than either feature alone.
- Temperature differential: create `Process temperature [K] - Air temperature [K]`. The two temperature columns are highly correlated (0.876107), but their gap may represent heat generated by the process after accounting for ambient conditions.
- Wear threshold features: create threshold or binned features from `Tool wear [min]`, such as high-wear flags near the upper quartile (162 min) or near the observed maximum range. Tool wear has the second strongest positive correlation with failure (0.105448).
- High-torque and low-speed regime flags: combine high `Torque [Nm]` with low `Rotational speed [rpm]`. Given the strong torque-speed inverse relationship and torque's stronger association with failure, this may identify overload-like operating states.

## Data Quality Concerns and Caveats

- The dataset is simulation-style and compact. It is useful for a hackathon prototype but may not reflect real plant data messiness, sensor drift, missing telemetry, delayed labels, or maintenance logs.
- The target is highly imbalanced at 3.39% failures, so naive classification can look good while missing most failures.
- `TWF`, `HDF`, `PWF`, `OSF`, and `RNF` should be treated as labels or explanatory diagnostics, not prediction-time features.
- `Product ID` and `UDI` should generally be excluded from model features. `UDI` can be useful only for ordered splitting experiments, and `Product ID` is row-specific.
- The lack of timestamp or run-to-failure sequence means the project cannot naturally model "failure in the next 24/48 hours" without defining a proxy framing.

## Open Questions for the Team

- How should we define "predict before it happens" when the dataset has no timestamp, no sequence length, and no explicit prediction horizon?
- Should the MVP optimize for detecting any `Machine failure`, or should we also present failure mode diagnostics as a secondary explanation layer?
- Should evaluation use a random stratified split, an ordered split by `UDI`, or both to show robustness?
- What operating cost tradeoff should guide threshold selection: prioritize catching more failures, or reduce false alarms for maintenance teams?
